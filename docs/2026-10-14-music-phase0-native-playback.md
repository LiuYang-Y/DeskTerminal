## 1. 这一步在整条路线上的位置

第一步（提交 `99eb62e`）已经回答过"合法 VIP 凭证下能不能拿到会员歌的完整 CDN URL"，但那一轮用的是 **PC 上的 Node 参考实现**。

第二步要证明的是**另一件事**：把这条链**搬进 Kotlin**、交给 **ExoPlayer**，还能不能真的放出声 ——
也就是 `09-原生重构评估.md` 里 Phase 0 的原话：

> **目标**：绕开登录，用现成 cookie 在原生层取到一首歌的真实 URL 并播出来。

**探针不做登录、不做搜索、不做 UI。** 登录属 Phase 1、搜索属 Phase 2，都不在这一步的射程内；
`songmid` / `media_mid` 作为**输入参数**由外部给（它们是公开标识，不是凭证）。

### 对原验收标准的一处修正

原文断言 ② 是「`sip[0] + purl` 拼出的 URL 能被 ExoPlayer 打开」。这条**证伪不了任何东西** ——
30 秒试听片段一样能被打开。按本项目"断言必须可被推翻"的要求，本步把它加强成两条：

1. CDN 返回的 `Content-Range` 总量 **等于**搜索响应声明的 `size128`（逐字节相等，不是"差不多"）；
2. 播放器报告的 `duration` 与搜索声明的 `interval` 吻合（试听片段会约 30s，立刻露馅）。

另外原文写的 `sip[0]` 在本条接口上**实测恒为空**，见 §4。

## 4. 断言②：从 `purl` 到"完整曲目"的字节级判据

### 4.1 `sip` 为空，必须兜底域名

参考实现的注释写过这件事，实测确认：`music.vkey.GetVkey / UrlGetVkey`
返回的 `midurlinfo` 齐全，但 **`sip` 是空数组**。没有兜底域名，`purl` 就是个裸文件名。

### 4.2 意外收获：明文那条路根本走不通，而 https 通

探针对每个候选域名都发一次 `Range: bytes=0-0`。实测（同一 `purl`，同一设备同一次运行）：

```
[A2] 候选域名 https://ws.stream.qqmusic.qq.com/      -> http=206 contentRange=OK(bytes 0-0/4317292)
[A2] 候选域名 https://dl.stream.qqmusic.qq.com/      -> http=206 contentRange=OK(bytes 0-0/4317292)
[A2] 候选域名 https://isure.stream.qqmusic.qq.com/   -> http=206 contentRange=OK(bytes 0-0/4317292)
[A2] 候选域名 https://sjy6.stream.qqmusic.qq.com/    -> http=206 contentRange=OK(bytes 0-0/4317292)
[A2] 候选域名 http://sjy6.stream.qqmusic.qq.com/     -> http=-1 contentRange=不可用(ERR IOException:
                                                       Cleartext HTTP traffic to sjy6.stream.qqmusic.qq.com not permitted)
```

最后一行是**真·反例**：`targetSdk 36` 下明文 HTTP 被系统直接拒。
参考实现用的默认域名是 `http://`，照搬到本工程会**当场失败**。

而同一 `purl` 挂到 **https** 域名上全部 206 —— 说明 https 不是"碰巧也能用"，是**这条路本来就有**。

**这条改写了一个实现决定**：正式实现不必开明文流量、不必给任何域名加
`networkSecurityConfig` 例外、不必 `usesCleartextTraffic`。
所以本次就连 debug 清单里也**刻意没有**这些例外（见 `app/src/debug/AndroidManifest.xml` 的注释）。

### 4.3 逐字节对照（断言②的真正判据）

| 标签 | 档位 | `purl` 长度 | `?` 前 | 文件名段首 4 | CDN 总字节 | 声明 `size128` | 相等？ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| VIP-晴天 | 128 | 216 | 22 | `M500` | 4,317,292 | 4,317,292 | ✅ |
| VIP-青花瓷 | 128 | 216 | 22 | `M500` | 3,830,789 | 3,830,789 | ✅ |
| VIP-稻香 | 128 | 216 | 22 | `M500` | 3,576,668 | 3,576,668 | ✅ |
| FREE-稻香童声版 | 128 | 243 | 22 | `M500` | 3,536,960 | 3,536,960 | ✅ |
| FREE-小星星 | 128 | 215 | 22 | `M500` | 2,244,230 | 2,244,230 | ✅ |
| VIP-晴天 | **flac** | 217 | **23** | **`F000`** | 55,397,039 | 55,397,039 | ✅ |

**6/6 逐字节相等。** `purl` 长度有 215/216/217/243 四种，差别全在 `?vkey=` 之后的签名串长度；
`?` 之前的文件名段恒为 22（128k）或 23（flac），说明服务端返回的是**规范化**过的文件名。

> 关于那个规范化：请求里送的是 `M500 + songmid + media_mid + .mp3`（36 字符），
> 服务端回来的是 `M500 + media_mid + .mp3`（22 字符）—— **它把 songmid 段丢了，只留 media_mid**。
> 这与第一步的自我证伪一致（`mediaId` 取 `media_mid` / `""` / `songmid` 结果相同），
> 且进一步解释了为什么"少送一段"不会出错。

**没有任何一首返回 0.92 MB 左右的试听片段**（`preview.trysize = 960,887`）：
6 首都等于各自的 `size128`，量级差了一个数量级。

## 5. 断言③：真的在出声（这一步最难证、也最容易被自己骗）

### 5.1 三层框架侧证据

**第一层 · AudioService 自己记的账**（`dumpsys audio` 的事件日志，带时间戳）：

```
14:51:53:597 new player piid:7671 uid/pid:10244/4345 type:android.media.AudioTrack
             attr:AudioAttributes: usage=USAGE_MEDIA content=CONTENT_TYPE_MUSIC flags=0xA00
14:51:53:612 player piid:7671 state:started
14:55:23:921 player piid:7671 state:paused
14:55:23:943 player piid:7671 state:stopped
14:55:23:943 releasing player piid:7671
```

- `uid/pid:10244/4345` 就是本应用（uid 10244 = `u0_a244`）；
- `type:android.media.AudioTrack` + `usage=USAGE_MEDIA` + `content=CONTENT_TYPE_MUSIC`
  —— 一个**真实存在的 AudioTrack**被创建并**启动**；
- 启动时刻 `14:51:53:612` 与探针日志里 ExoPlayer 的 `STATE READY`（`14:51:53.639`）**相差 27ms**；
- 存活 `14:51:53.597 → 14:55:23.921` = **210.3s**，与探针的 `maxsec=210` 吻合到 0.3s。

**这不是应用自报的**，是 AudioService 的 PlayerBase 记账。应用想伪造也伪造不了这条。

**第二层 · 混音器里的轨道**（`dumpsys media.audio_flinger`，播放中 t≈8s）：

```
  2 Tracks of which 2 are active
    Type     Id Active Client Session Port Id S  Flags   Format Chn mask  SRate ST Usg CT  G db ...
           1116    yes   4345    7017    1193 A  0x000 00000001 00000003  44100  3   1  2   -52 ...
```

本进程（`Client=4345`）的轨道 `Active=yes`，`44100Hz` / `Usg=1`(MEDIA) / `CT=2`(MUSIC)。

**第三层 · 零欠载**：同一条轨道上 `Underruns=0`；31 分钟窗口的 **25 个播放样本，`our_under` 全是 0**
—— 混音器一次都没把这条轨道饿着。

### 5.2 反例对照（没有这个，上面三条都可能是"恒为真"的假证据）

| 反例 | 观察 |
| --- | --- |
| **播放停止后**（探针 `maxsec` 到点） | `dumpsys audio` 里 `u/pid:10244/` **一条都没有**；`audio_flinger` 里本进程轨道**消失**（扫描结果："无：本进程轨道已消失"） |
| **明文域名** | `http://sjy6...` → `Cleartext HTTP traffic ... not permitted`（见 §4.2） |
| **音量变 0 之后**（15:19:21 起，31 分钟那次的后半段） | 轨道仍旧 `Active=yes`、`Underruns=0`、`pbcfg=started`、CPU 不变（~5%） |
| **探针不跑时** | 采样里的 `pbcfg` 是 `-`、`focus` 是 `N`、CPU 是 `0.0` |

第 3 条特别有用：它证明这些判据**不依赖音量**，也就不受"谁动了音量"的干扰。

### 5.3 `currentPosition` 的单调性 —— 以及一次工具的假阴性

| 运行 | 采样数 | 真回退 | 循环回绕 | 结论 |
| --- | --- | --- | --- | --- |
| 晴天 210s 播放（`assert3`） | 210 | **0** | 0 | 位置 340 → 210,073 ms 单调推进 |
| 青花瓷 45s 播放 | 45 | **0** | 0 | 344 → 44,449 ms |
| 小星星 45s 播放 | 45 | **0** | 0 | 582 → 44,680 ms |
| 晴天 **1900s** 播放（30 分钟功耗那次，**第一版判据**） | 1900 | 0 | 7 | 工具误判为"不成立"，见下文 |
| 晴天 **600s** 播放（**修好判据后**的真机复验） | 600 | **0** | **2** | 工具与离线复核都判"成立"，见 §5.4 |

210s 那次还额外算了一个数：末位置 / 窗口时长 = **209,733 ms / 209.676 s = 1.00027**，
即**位置推进与墙上时钟的偏差只有 0.03%** —— 音频时钟按真实速率在走，不是"报了个数"。

**必须记下来的一次工具故障（假阴性）**：1900s 那次的原始日志里，第一版判据输出了

```
15:34:54.368 [A3] 断言③ **不成立**，见上
```

原因是它把"位置变小"一律算成回退。查原始记录，这 7 次全都是：

```
15:07:40.404 [TICK] **位置回退** 269312 -> 548
15:12:10.091 [TICK] **位置回退** 269278 -> 530
15:16:39.742 [TICK] **位置回退** 269056 -> 288
15:21:09.372 [TICK] **位置回退** 268849 -> 290
15:25:39.030 [TICK] **位置回退** 268782 -> 17
15:30:08.691 [TICK] **位置回退** 268825 -> 15
15:34:38.333 [TICK] **位置回退** 268762 -> 13
```

`269xxx → ~0`，两次间隔恒为 **269 秒**（t=270/539/808/1077/1346/1615/1884 s）——
**这是单曲循环的回绕**，与曲长 269.746s 吻合。也就是说：**播放是好的，是判据错了。**

处置（三步都做了，一步不省）：

1. **不抹掉那行"不成立"**。原始日志 `probe-30min.log` 原样保留，本报告公开引用它 —— 掩盖掉就看不出结论是怎么变的。
2. **修判据**：回绕需同时满足「开了 `REPEAT_MODE_ONE`」+「上一位置 ≥ 95% 曲长」+「新位置 < 2000ms」，
   三者缺一仍算真回退。并在日志里把回绕间隔与曲长并排打出来，让"数量级吻合"本身成为证据。
3. **用同一份原始数据离线复核**（`classify-wraps.py`，判定规则与修好后的探针一致）：

```
TICK 采样数 : 1900
曲长(dur)   : 269746 ms
循环回绕    : 7 次  -> [(270, 269312, 548), (539, 269278, 530), (808, 269056, 288),
                        (1077, 268849, 290), (1346, 268782, 17), (1615, 268825, 15),
                        (1884, 268762, 13)]
真回退      : 0 次  -> []
回绕间隔(s) : [269, 269, 269, 269, 269, 269]
均值        : 269.000s  (对照曲长 269.746s)  偏差 0.746s
重新判定    : 断言③ 成立（真回退 0 次；回绕不计入）
```

0.746s 的偏差正是 1s 采样粒度本身 —— 7 段回绕间隔全等，这条判据自己也经得起推敲。

## 10. 踩坑清单（Phase 1+ 会再遇到的）

1. **`singleInstance` 会吞掉第二次 `am start`**
   症状：系统打印 `Activity not started, intent has been delivered to currently running top-most instance.`，
   探针**看起来跑过了却没有新日志** —— 极易误判成"这次请求失败"。
   处置：`onNewIntent` → `setIntent` + `recreate()`。
2. **`dumpsys media.audio_flinger` 的轨道行有两种形状**（有的行首有 `Type` 列，有的没有）。
   按单一形状写死偏移会**静默漏检本进程的轨道**（第一版 `fl_hits` 恒为 0）。
   正确做法：先判断 `yes/no` 落在第几个字段，再以它为基准取 `Client`，列偏移相对 Client 固定。
3. **`FrmCnt` 不是累计计数器**，是轨道的**缓冲帧数**（实测 960 / 22050 / 99944 正好对应
   48000×0.02s / 44100×0.5s / 192000×0.52s）。拿它当"真的在出声"的判据会得出**错误结论**
   （它在播放中恒定不变）。真正是累计量的是 `Underruns`。
4. **单曲循环的回绕会被"位置单调性"判据误判成异常**（见 §5.3）。判据要显式排除回绕。
5. **`MSYS_NO_PATHCONV=1` 下 `/d/...` 不再被转换** —— 此时必须用 `D:/...`；
   反过来，不设这个变量时给 adb 传 `/data/local/tmp/...` 会被改写成 `C:\...`。
   两个方向都会静默出错。
6. **`adb usb` 会让设备在"拔着线"的状态下直接失联**。切回 USB 模式前要确认线在。
7. **purl 的文件名段被服务端规范化**（`songmid` 段被丢掉，只留 `media_mid`），见 §4.3。
8. **MIUI 的后台清理会造成假阴性**：长测前先 `dumpsys deviceidle whitelist +<pkg>`，测完移除。
9. **本机没有 `media` 命令**（`/system/bin/sh: media: inaccessible or not found`），
   调音量只能 `input keyevent 24/25`；而且**音量不一定是脚本设定值**，要逐样本记录实际值。
